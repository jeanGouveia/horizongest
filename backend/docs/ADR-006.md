# ADR-006: Arquitetura dos Consumers

**Status:** Aceito
**Data:** 31/07/2026
**Decisores:** Software Architect Senior
**Contexto:** Sprint 5C.3 - Email Consumer

---

## Contexto e Problema

O HorizonGest implementou uma infraestrutura de publicação de eventos (Sprint 5C.2 e 5C.2.1) utilizando o Outbox Pattern e RabbitMQ. Agora é necessário implementar consumidores para processar esses eventos (Email, Webhook, iFood).

**Problemas a resolver:**

1. **Como estruturar consumidores para que sejam independentes da infraestrutura de produção?**
   - Consumidores não devem conhecer Dispatcher, Outbox, EventPublisher
   - Consumidores devem ser desacoplados da lógica de negócio principal

2. **Como garantir que consumidores possam ser substituídos ou estendidos?**
   - Diferentes providers (SMTP, SendGrid, SES, Mailgun)
   - Diferentes brokers (RabbitMQ, Kafka, Redis Streams)

3. **Como garantir idempotência em consumidores?**
   - Sistema usa At Least Once delivery
   - Consumidores DEVEM ser idempotentes

4. **Como criar uma arquitetura reutilizável para múltiplos consumidores?**
   - Email, Webhook, iFood devem seguir o mesmo padrão
   - Evitar duplicação de código

---

## Decisão

### Princípios Arquiteturais

1. **Independência da Infraestrutura de Produção**
   - Consumidores NÃO conhecem Dispatcher
   - Consumidores NÃO conhecem Outbox
   - Consumidores NÃO conhecem EventPublisher (do lado do produtor)
   - Consumidores conhecem apenas: Broker → Evento → Ação

2. **Interface-based Design**
   - Todas as dependências externas são abstraídas via interfaces
   - Providers (Email, Webhook, iFood) são interfaces
   - Templates são interfaces
   - Isso permite substituição e testabilidade

3. **Idempotência Obrigatória**
   - Todo consumidor DEVE implementar proteção contra duplicação
   - Store de idempotência pode ser in-memory, database ou Redis
   - Verificar EventID antes de processar

4. **Observabilidade**
   - Logs estruturados para todas as operações
   - Evento recebido, ignorado, processado, falha, retry
   - Tempo de processamento

### Arquitetura Proposta

```
┌─────────────────────────────────────────────────────────────┐
│                     Message Broker                           │
│                  (RabbitMQ, Kafka, etc.)                     │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ↓
┌─────────────────────────────────────────────────────────────┐
│                  Consumer                                   │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  - Broker Connection (específico ao broker)          │  │
│  │  - Queue/Topic                                        │  │
│  │  - Provider (Interface)                               │  │
│  │  - IdempotencyStore                                   │  │
│  │  - Templates (Interface)                              │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                              │
│  Flow:                                                       │
│  1. Consume mensagem do broker                             │
│  2. Desserializar evento                                   │
│  3. Verificar idempotência (EventID)                       │
│  4. Processar evento (Template → Provider)                │
│  5. Marcar como processado                                 │
│  6. Ack mensagem                                           │
└─────────────────────────────────────────────────────────────┘
                        │
                        ↓
┌─────────────────────────────────────────────────────────────┐
│                  Provider (Interface)                        │
│  - Send(ctx, data) error                                    │
│  - Close() error                                            │
│                                                              │
│  Implementações:                                             │
│  - LogProvider (desenvolvimento/teste)                      │
│  - RealProvider (produção: SMTP, SendGrid, etc.)           │
└─────────────────────────────────────────────────────────────┘
```

### Exemplo: Email Consumer

```go
// Interface para envio de email
type EmailProvider interface {
    Send(ctx context.Context, email Email) error
    Close() error
}

// Implementação de log (desenvolvimento)
type LogEmailProvider struct{}

func (p *LogEmailProvider) Send(ctx context.Context, email Email) error {
    log.Printf("[EMAIL] To: %s, Subject: %s", email.To, email.Subject)
    return nil
}

// Implementação SMTP (produção)
type SMTPEmailProvider struct {
    host string
    port int
    auth smtp.Auth
}

func (p *SMTPEmailProvider) Send(ctx context.Context, email Email) error {
    return smtp.SendMail(
        fmt.Sprintf("%s:%d", p.host, p.port),
        p.auth,
        "noreply@horizongest.com",
        []string{email.To},
        []byte(email.Body),
    )
}

// Consumer principal
type EmailConsumer struct {
    connection      *amqp.Connection
    queue           string
    emailProvider   EmailProvider  // Interface
    idempotencyStore *IdempotencyStore
    templates       map[string]Template
}

func (c *EmailConsumer) Start(ctx context.Context) error {
    // Consume do RabbitMQ
    msgs, _ := channel.Consume(c.queue, ...)
    for msg := range msgs {
        c.processMessage(ctx, msg)
    }
}
```

## Consequências

### Positivas

1. **Desacoplamento**
   - ✅ Consumidores são independentes da infraestrutura de produção
   - ✅ Mudanças no Dispatcher/Outbox não afetam consumidores
   - ✅ Consumidores podem ser desenvolvidos em paralelo

2. **Substituibilidade**
   - ✅ Provider pode ser trocado sem alterar o consumidor
   - ✅ LogProvider para desenvolvimento, SMTP para produção
   - ✅ Fácil adicionar novos providers (SendGrid, SES, Mailgun)

3. **Testabilidade**
   - ✅ Mock implementations para testes unitários
   - ✅ LogProvider permite testar sem envio real
   - ✅ IdempotencyStore pode ser mockado

4. **Reutilização**
   - ✅ Padrão pode ser replicado para Webhook, iFood, etc.
   - ✅ Código compartilhado (idempotência, templates)
   - ✅ Consistência entre consumidores

5. **Escalabilidade**
   - ✅ Múltiplos consumidores podem rodar em paralelo
   - ✅ RabbitMQ distribui mensagens entre instâncias
   - ✅ Idempotência compartilhada via store persistente

### Negativas

1. **Acoplamento ao Broker**
   - ⚠️ Consumidores são específicos ao broker (RabbitMQ, Kafka, etc.)
   - ⚠️ Se precisar trocar broker, precisa criar novo consumidor
   - **Mitigação:** Lógica de negócio é independente, apenas consumo é específico

2. **Complexidade Inicial**
   - ⚠️ Mais código devido a interfaces
   - ⚠️ Necessário implementar múltiplos arquivos
   - **Mitigação:** Padrão é reutilizável, benefícios superam custo inicial

3. **Idempotência Manual**
   - ⚠️ Cada consumidor deve implementar idempotência
   - ⚠️ Store in-memory não persiste entre restarts
   - **Mitigação:** Documentação clara, store persistente em produção

## Alternativas Consideradas

### Alternativa 1: Consumidor Conhecendo Dispatcher

**Descrição:** Consumidor chama diretamente o Dispatcher para obter eventos.

**Por que não foi escolhida:**
- ❌ Alto acoplamento entre consumidor e infraestrutura de produção
- ❌ Consumidor depende de implementação interna do Dispatcher
- ❌ Dificulta troca de broker
- ❌ Viola princípio de independência

### Alternativa 2: Evento com Callback

**Descrição:** Evento inclui URL de callback para notificação.

**Por que não foi escolhida:**
- ❌ Aumenta complexidade do evento
- ❌ Produtor precisa conhecer consumidores
- ❌ Dificulta adicionar novos consumidores
- ❌ Não segue padrão pub/sub

### Alternativa 3: Polling no Banco

**Descrição:** Consumidor faz polling direto na tabela outbox_events.

**Por que não foi escolhida:**
- ❌ Consumidor conhece schema interno (outbox_events)
- ❌ Acoplamento direto ao banco de dados
- ❌ Polling é menos eficiente que mensageria
- ❌ Viola separação de responsabilidades

## Perguntas Frequentes

**Q: Por que consumidores não conhecem o Dispatcher?**

A: Dispatcher é parte da infraestrutura de produção (lado do produtor). Consumidores devem ser independentes para:
- Evitar acoplamento
- Permitir desenvolvimento em paralelo
- Facilitar troca de broker
- Seguir princípio de separação de responsabilidades

**Q: Por que utilizar interfaces para Providers?**

A: Interfaces permitem:
- Substituição de implementação (Log → SMTP → SendGrid)
- Testabilidade com mocks
- Extensibilidade para novos providers
- Isolamento de lógica específica

**Q: Por que consumidores podem ser específicos ao broker?**

A: Consumo de mensagens é naturalmente específico ao broker:
- RabbitMQ usa AMQP
- Kafka usa protocolo próprio
- Redis Streams usa protocolo próprio

No entanto, a **lógica de negócio** (templates, idempotência, providers) é independente e pode ser reutilizada.

**Q: Como trocar RabbitMQ por Kafka no futuro?**

A: Criar novo consumidor para Kafka:
```go
type KafkaEmailConsumer struct {
    processor *EmailProcessor  // Lógica reutilizável
    consumer  *kafka.Consumer // Específico do Kafka
}

// EmailProcessor contém a lógica independente
type EmailProcessor struct {
    emailProvider   EmailProvider
    idempotencyStore *IdempotencyStore
    templates       map[string]Template
}
```

**Q: Por que idempotência é obrigatória?**

A: Sistema usa At Least Once delivery:
- Eventos podem ser duplicados (Dispatcher cair após publicar)
- Consumidores DEVEM ignorar eventos já processados
- Sem idempotência, emails/webhooks seriam enviados duplicados
