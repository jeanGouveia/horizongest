# ADR-003: Por que Repository Pattern?

## Status

Aceito

## Contexto

O sistema precisa de uma camada de persistência que:
- Abstraia a implementação de banco de dados
- Permita testabilidade dos services
- Mantenha o domínio puro (sem dependência de infraestrutura)
- Facilite mudanças de tecnologia de persistência

## Decisão

Utilizamos Repository Pattern com interfaces no pacote `ports` e implementações GORM no pacote `infra/repository`.

**Estrutura:**
- `ports/*_repository.go`: Interfaces definindo contratos
- `infra/repository/gorm_*_repository.go`: Implementações GORM
- Services dependem apenas das interfaces (ports)
- Domain não conhece repositories

**Fluxo:**
```
Handler
  ↓
Service (depende de ports)
  ↓
Repository (implementa ports)
  ↓
Database
```

## Consequências

### Positivas
- Domínio completamente puro (sem dependência de infraestrutura)
- Services testáveis com mocks
- Fácil mudar de GORM para outra tecnologia
- Separação clara de responsabilidades
- Conformidade com princípio #1 do 06-DOMINIO.md

### Negativas
- Boilerplate adicional (interfaces + implementações)
- Curva de aprendizado inicial

## Alternativas Consideradas

1. **Acesso direto ao banco no service:** Rejeitado - viola pureza do domínio
2. **Active Record:** Rejeitado - acopla domínio à infraestrutura
3. **Data Mapper sem interfaces:** Rejeitado - dificulta testabilidade
