# ADR-005: Por que Snapshot Builder ficou como dívida técnica?

## Status

Aceito

## Contexto

Atualmente o Repository cria os Snapshots durante CreateOrder. Esta foi uma decisão consciente para manter o MVP simples, evitando a criação de serviços adicionais e mantendo a responsabilidade de montagem de snapshots dentro da camada de persistência.

## Decisão

Deixamos a migração da responsabilidade de montar Snapshots para um Domain Service (SnapshotBuilder ou StockService) como dívida técnica documentada em 07-TECH-DEBT.md.

**Fluxo Atual (MVP):**
```
OrderService
  ↓
OrderRepository (cria snapshot)
  ↓
Banco de Dados
```

**Fluxo Futuro Desejado (Pós-MVP):**
```
OrderService
  ↓
SnapshotBuilder (monta snapshot)
  ↓
OrderRepository (persiste apenas)
  ↓
Banco de Dados
```

## Consequências

### Positivas (Decisão Atual)
- MVP simples e funcional
- Menos código para manter
- Menos complexidade inicial
- Foco em funcionalidades core

### Negativas (Decisão Atual)
- Repository com responsabilidade além de persistência
- Lógica de snapshot misturada com persistência
- Dificuldade de reutilização em outros contextos
- Testabilidade limitada da lógica de snapshot

### Positivas (Fluxo Futuro)
- Separação de responsabilidades
- Reutilização em múltiplos contextos
- Testabilidade independente
- Manutenibilidade facilitada

## Quando Implementar

Esta mudança deve ser considerada quando:
- O sistema evoluir para além do MVP
- A lógica de snapshot se tornar mais complexa
- Houver necessidade de reutilizar a lógica de snapshot em múltiplos contextos

## Restrições Atuais

Esta mudança NÃO deve ser implementada agora. Ela fica registrada apenas como evolução arquitetural planejada:
- Não mover código
- Não criar SnapshotBuilder
- Não criar novos Services
- Não criar interfaces
- Não alterar Repository
- Não alterar injeção de dependências
- Não alterar CreateOrder
- Não alterar arquitetura do MVP
