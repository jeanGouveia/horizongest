# ADR-002: Por que Active e DeletedAt coexistem?

## Status

Aceito

## Contexto

O sistema precisa distinguir entre dois conceitos distintos:
1. Disponibilidade operacional (o item pode ser utilizado?)
2. Existência lógica (o registro foi removido?)

## Decisão

Utilizamos dois campos com responsabilidades distintas:

**Active:**
- Significa exclusivamente "Pode ser utilizado pelo negócio?"
- Não representa exclusão
- Não representa arquivamento
- Não representa histórico
- Exemplos: Produto disponível, Ingrediente disponível

**DeletedAt:**
- Significa "O registro foi removido logicamente"
- Soft delete
- Registro não aparece em consultas normais
- Continua existindo para auditoria
- Continua preservando relacionamentos históricos

**Separação de responsabilidades:**
- Produto fora do cardápio: active = false, deleted_at = NULL
- Produto removido: active = false, deleted_at != NULL
- Nunca existirão: active = true, deleted_at != NULL

## Consequências

### Positivas
- Responsabilidades claras e separadas
- Flexibilidade para diferentes estados
- Conformidade com princípio #14 do 06-DOMINIO.md
- Auditoria preservada com soft delete

### Negativas
- Dois campos para gerenciar
- Complexidade adicional em queries (filtrar por deleted_at IS NULL)

## Alternativas Consideradas

1. **Apenas active:** Rejeitado - não distingue exclusão de indisponibilidade
2. **Apenas deleted_at:** Rejeitado - não permite indisponibilidade temporária
3. **Status enum:** Rejeitado - viola princípio de responsabilidade única
